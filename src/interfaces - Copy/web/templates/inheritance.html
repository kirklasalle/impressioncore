Working with Inheritance in UKS

Understanding Inheritance

Inheritance is a key feature of the Universal Knowledge Store (UKS) that allows knowledge nodes to automatically receive attributes and properties from their parent nodes. This creates an efficient and consistent way to represent hierarchical knowledge.

Creating Inheritance Relationships

When creating nodes with inheritance relationships, you need to:

  1. Create the nodes individually
  2. Then explicitly add parent-child relationships using the add_relationship method

from impressioncore.uks import UniversalKnowledgeStore

# Initialize the UKS
uks = UniversalKnowledgeStore()

# Create parent node
vehicle = uks.create_node(
    label="Vehicle",
    attributes={
        "has_wheels": True,
        "movable": True,
        "purpose": "transportation"
    }
)

# Create child node
car = uks.create_node(
    label="Car",
    attributes={
        "passenger_capacity": 5,
        "typical_doors": 4,
        "requires_driver": True
    }
)

# Establish inheritance relationship
uks.add_relationship(
    parent=vehicle,
    child=car,
    relationship_type="is_a"
)

# Now car inherits attributes from vehicle
print(car["has_wheels"])    # True (inherited)
print(car["movable"])       # True (inherited)
print(car["typical_doors"]) # 4 (defined directly)

How Inheritance Works

When you access an attribute on a node, the UKS follows these steps:

  1. Check if the attribute is defined directly on the node
  2. If not found, check each parent node in order of relationship strength
  3. Continue up the hierarchy until the attribute is found or all ancestors are checked
  4. If the attribute is not found anywhere, return None or raise an exception (configurable)

Note: Inheritance in UKS is dynamic and computed at access time, not at relationship creation time. This means changes to parent nodes are immediately reflected in child nodes.

Overriding Inherited Attributes

Child nodes can override attributes inherited from parents by defining the same attribute locally:


# Create another child of Vehicle
motorcycle = uks.create_node(
    label="Motorcycle",
    attributes={
        "has_wheels": 2,     # Overrides the parent's value (True)
        "passenger_capacity": 2,
        "requires_helmet": True
    }
)

# Establish inheritance relationship
uks.add_relationship(parent=vehicle, child=motorcycle, relationship_type="is_a")

# The motorcycle has_wheels value overrides the parent's value
print(motorcycle["has_wheels"])      # 2 (overridden)
print(motorcycle["movable"])         # True (inherited)
print(motorcycle["requires_helmet"]) # True (defined directly)

Multiple Inheritance

UKS supports multiple inheritance, allowing a node to inherit from multiple parents:


# Create another parent node
machine = uks.create_node(
    label="Machine",
    attributes={
        "man_made": True,
        "requires_maintenance": True,
        "has_parts": True
    }
)

# Add a second parent to the car node
uks.add_relationship(parent=machine, child=car, relationship_type="is_a")

# Car now inherits from both Vehicle and Machine
print(car["movable"])               # True (from Vehicle)
print(car["requires_maintenance"])  # True (from Machine)
print(car["passenger_capacity"])    # 5 (defined directly)

Inheritance Priority

When multiple parents define the same attribute, the inheritance priority is determined by:

  1. The order in which relationships were added (earlier takes precedence)
  2. The relationship strength (higher strength takes precedence)
  3. Custom priority rules defined in the UKS configuration

# Define another parent node with conflicting attribute
electric_device = uks.create_node(
    label="ElectricDevice",
    attributes={
        "requires_maintenance": False,
        "power_source": "electricity"
    }
)

# Create a node with potential attribute conflict
electric_car = uks.create_node(
    label="ElectricCar",
    attributes={
        "battery_capacity": "75 kWh"
    }
)

# Add relationships with different strengths to control inheritance priority
uks.add_relationship(
    parent=car, 
    child=electric_car, 
    relationship_type="is_a",
    properties={"strength": 0.8}
)

uks.add_relationship(
    parent=electric_device, 
    child=electric_car, 
    relationship_type="is_a",
    properties={"strength": 0.9}  # Higher strength takes precedence
)

# The higher-strength relationship wins for conflicting attributes
print(electric_car["requires_maintenance"])  # False (from ElectricDevice)

Checking Inheritance Relationships

The UKS provides several methods to inspect inheritance relationships:


# Check if a node inherits from another node
is_vehicle = car.inherits_from(vehicle)
print(f"Car inherits from Vehicle: {is_vehicle}")  # True

# Get all parent nodes
parents = electric_car.get_parents()
print(f"ElectricCar parents: {[p['label'] for p in parents]}")  # ["Car", "ElectricDevice"]

# Get all ancestor nodes (parents, grandparents, etc.)
ancestors = electric_car.get_ancestors()
print(f"ElectricCar ancestors: {[a['label'] for a in ancestors]}")  

# Check inheritance by label
if electric_car.inherits_from_label("Vehicle"):
    print("ElectricCar is a type of Vehicle")  # This will print

Inherited Attribute Resolution

To see exactly where an attribute comes from in the inheritance chain:


# Get the source of an inherited attribute
source = electric_car.get_attribute_source("movable")
print(f"'movable' attribute comes from: {source['label']}")  # "Vehicle"

# Get all inherited attributes and their sources
inherited = electric_car.get_inherited_attributes(include_sources=True)
for attr, details in inherited.items():
    print(f"{attr}: {details['value']} (from {details['source']['label']})")

# Get only directly defined attributes (not inherited)
direct_attrs = electric_car.get_direct_attributes()
print(f"Direct attributes: {direct_attrs}")  # {"battery_capacity": "75 kWh"}

Inheritance Best Practices

  • Plan Your Hierarchy: Design your inheritance structure carefully to avoid deep or overly complex hierarchies.
  • Use Clear Relationship Types: Use "is_a" specifically for inheritance; use other relationship types for non-inheritance associations.
  • Avoid Inheritance Cycles: Ensure that no node is both an ancestor and descendant of another node.
  • Document Overrides: When overriding an inherited attribute, consider adding a metadata note explaining why.
  • Be Cautious with Multiple Inheritance: Multiple inheritance can become complex; use relationship strengths to clarify priority.
  • Use Abstract Base Nodes: Create "concept" or "abstract" nodes that define common attributes shared by multiple child nodes.
